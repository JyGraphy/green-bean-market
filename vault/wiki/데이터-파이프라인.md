## 실행 순서

`scrapers/run_all.py` → GitHub Actions에서 매일 실행.

1. 스크래퍼 15종 순차 실행 (개별 실패는 격리 — 정상 store는 커밋됨)
2. `scripts/check_links.py` — 404/410만 제거, 403/429는 보존
3. `scripts/enrich_process.py` — '알수없음' 상품의 가공방식 상세페이지 보강
4. `scripts/generate_sql.py` — 파생 파일 재생성
5. `scripts/site_selfcheck.py` — **링크가 통째로 깨진 공급사를 판정** (아래 참조)
6. `scripts/validate_data.py` — 커밋 직전 검증 게이트
7. 커밋·푸시 (rebase 후 최대 3회 재시도)
8. `scripts/healthcheck.py` — 배포 대기 후 **같은 잡에서** 라이브 점검
   (별도 `sitecheck.yml` KST 07:15 도 유지)

전체 소요 약 16분(2026-08-19·20 실측). 매 실행 끝에 **단계별 소요시간**이 출력된다.

## 06시 작업은 세 가지 일이다

한 잡에 성격이 다른 일이 섞여 있어, 최적화할 때 뭉뚱그리면 안 된다.

| 하는 일 | 비용 구조 | 공급사가 늘면 |
|---|---|---|
| 판매현황·가격·이름 정확성 | 목록 1페이지에 상품 수십 개 | 페이지 수에 비례 — 상대적으로 쌈 |
| **죽은 링크 검사** | **상품 1개당 요청 1건** | **정비례로 폭증 — 확장 시 병목** |
| 가공방식 보강 | '알수없음' 상품만 | 자연히 줄어듦 |

**표본 검사는 도입하지 않았다.** 06시 작업에는 판매현황·정보 정확성 점검이 함께
걸려 있어 함부로 줄일 대상이 아니다. 대신 낭비만 제거했다(HEAD 타임아웃 시 GET 생략).

## 자가 점검 — 보류 신호를 읽는 사람 (2026-08-20 신설)

`check_links` 는 한 store의 dead 비율이 30%를 넘으면 **제거를 보류**한다. 올바른
설계지만, **그 신호를 아무도 읽지 않으면 죽은 링크가 계속 노출된다.**
실제로 모모스커피 115개가 100% dead 상태로 방치됐다.

`site_selfcheck.py` 가 그 자리를 메운다 — 갱신 직후 판정하고 **시끄럽게 만든다**:

| 판정 | 처리 |
|---|---|
| 🔴 store 링크 전멸 / 제거 보류 | 종료코드 1 → 잡 빨간 X → 알림 메일 |
| 🟡 부분 dead · 전부 모호 응답(봇차단) | 경고만 |

보고서는 `vault/raw/qa/<날짜>-사이트점검.md` 로 남고 함께 커밋된다. 토큰 0.

## ⏳ 조치 필요

| 우선순위 | 항목 | 내용 |
|---|------|------|
| 1 | `scripts/scrape-falcon.js` 폐기 | `START_ID + i` 순차 ID 부여 — 규칙 2 금지 패턴. 파이프라인 밖 수동 도구이나 재사용 시 중복 ID 발생. 주석 `START_ID=850`도 낡음(실제 최대 1417) |
| 2 | 모모스·커피리브레 통합 | 자체 저장 로직 사용 → `common.to_products` + `update_json`으로 통합하면 `clean_name` 미적용 문제(`[재입고]` 잔류) 해소 |
| 3 | 아얀투 이름 파싱 | `parse_v2` 폴백이 카드 전체 텍스트를 상품명으로 캡처 → 22건 오염, origin 20/20 미상 |
| 4 | `abs_url` 통일 | `cobeans:32`, `blessbean:29`가 직접 URL 조립 (현재 결과는 정상) |
| 5 | 스크래퍼 병렬화 | 15개가 **순차** 실행 중. 서로 다른 호스트라 병렬화해도 호스트당 부하는 안 늘지만, 전부 `products.json` 한 파일을 읽고-쓰므로 **락 또는 store별 파일 분리가 먼저** 필요하다. 단계별 소요시간 데이터를 보고 결정한다 |

## 해결된 것 (2026-08-19~20)

- **모모스 플랫폼 이전** — cafe24 → 아임웹. 저장된 115개 URL 전량 404였다.
  스크래퍼를 새 구조(`/Product_GreenBean/?idx=<숫자>`)로 재작성하고 27개로 교체.
  취급 품목이 실제로 줄어든 것이라 급감 가드를 `FORCE_DATA_UPDATE=1` 로 우회했다.
- **급감 가드에 우회 경로 신설** — 정당한 감소를 반영할 방법이 없어 영구히 막혔다.
  0개 수집은 여전히 어떤 경우에도 우회되지 않는다.
- **`run_all.py` 타임아웃** — 하위 프로세스에 시간 제한이 없었다(예방 조치로 추가.
  실제 장애가 있었던 것은 아니다). 잡 상한 60분도 함께 설정.
- **푸시 충돌로 갱신분 유실** — 수집 15분 동안 main 이 앞서 나가면 push 가 거부돼
  그날 갱신이 통째로 버려졌다(2026-08-20 실제 발생). 워크플로 5종 전부
  rebase 후 3회 재시도하도록 수정.
